## 1. 动作审查 (State Review)：主结论成立，归因反了

### 1.1 复现结果

`executor.rs:93-101` 的确在 `mouse_click` / `click_element` / `click_mark` / `press_key` / `hotkey`
五类动作前同步调用一次 `capture_active_window_state()`；`window.rs:65-84` 的 `review_action_loop`
无条件 `sleep(80ms)` 后再调一次。调用次数与位置与文档描述一致。

| 项 | 文档值 | 我的实测 |
|:--|--:|--:|
| `System::new() + refresh_processes()` | 2.77 ms | 2.33 / 2.35 ms |
| `sys.refresh_processes()`（实例复用） | 2.40 ms | 2.56 ms |
| `capture_active_window_state()` 单次 | 14.73 ms | **20.30 / 21.39 ms** |
| 单次动作前后 2 次 | 29.46 ms | **40.60 ms** |
| 叠加 80 ms sleep 的点击总延迟 | ~110 ms | **120.6 ms** |

> ⚠️ 顺带修正一处：文档把 2.77 → 2.40 ms 说成"复用实例提速 1.16x"，暗示复用有价值。实测复用是
> **−0.24 ms（噪声，反而略慢）**——2.4 ms 是 `refresh_processes()` 本身的成本，两条路径都要付。

### 1.2 但归因是错的：贵的不是进程扫描，是 xcap

`window_stage` 按 `window.rs:517-587` 逐行复刻并分段计时（7 个在屏窗口 / 813 进程）：

| 阶段 | 中位耗时 | 占比 |
|:--|--:|--:|
| ① `xcap::Window::all()` 仅枚举 | 7.70 ms | 38% |
| ② `System::new() + refresh_processes()` | 2.35 ms | **11%** |
| ③ xcap 逐窗属性访问（title/app_name/rect/…，7 窗 × 8 次调用） | ~9.0 ms | 44% |
| ④ 逐窗 O(窗口×进程) 名字匹配 | ~1 ms | 5% |

文档写的"内部执行全量进程枚举" **只占 11%**。按文档的方案字面执行（"免全量进程扫描"），
单次只能省 2.4 ms，两次 4.8 ms——离"立省 30 ms"差一个数量级。

### 1.3 方案本身成立，而且比文档说的更强

用 `CGWindowListCopyWindowInfo(kCGWindowListOptionOnScreenOnly)` 一次调用即带回
title / owner / pid / bounds（macOS 上就是给这个用途设计的 API）：

| 路径 | 中位耗时 |
|:--|--:|
| 生产 `capture_active_window_state()` | 21.39 ms |
| 直连 `CGWindowListCopyWindowInfo` + 逐窗解析 title/owner/pid | **0.14 ms** |

**单次省 21.25 ms（99%），两次动作省 42.5 ms。** 项目已依赖 `core-graphics 0.23`（目前只用于
`input.rs` 的注入），无需新增依赖。

> 补充：该开销随**在屏窗口数**增长（我的两次运行窗口数 7 / 14，耗时 20.3 / 21.4 ms），
> 因此文档的绝对值可复现性依赖环境，写"14.73 ms"时应附窗口数。

## 3. list_processes (7.4)：结论对，归因错，方案几乎没有价值

| 项 | 文档值 | 我的实测 |
|:--|--:|--:|
| 全量 `list_processes(None)` | 2.94 ms | 2.65 ms |
| 关键词过滤 `list_processes(Some("cargo"))` | 3.01 ms | 2.68 ms（本机 0 命中） |
| **仅 `sys.refresh_processes()`（归因基线）** | 未测 | **2.55 ms** |
| 参考实现：refresh + 先过滤再物化 | 未测 | 2.26 ms |

结论"**过滤不省时**"✅。但文档把原因归为"先对全系统所有进程无条件执行
`proc_data.cmd().to_vec()` 和 `name.to_string()` 的全量堆内存克隆"（`process.rs:54-55`）——
代码位置描述准确，**但量级判断错误**：

- 全量物化 − 过滤物化 = 2.65 − 2.68 = **0.03 ms**
- `refresh + 物化` − `仅 refresh` = 2.65 − 2.55 = **0.10 ms**
- 也就是说**跳过全部克隆最多省 0.10 ms，占总耗时 4%**
- 真正的成本是 `process.rs:45` **每次调用都 `sys.refresh_processes()`**（2.55 ms，96%）

**对应的 P2-F 建议（"过滤前置"）nearly 无收益。** 有意义的做法是给
`refresh_processes()` 加 TTL 缓存（`get_cached_system()` 已持有持久 `System`，只需跳过刷新），
可把 2.65 ms 降到 ~0.15 ms，约 17x。

## 4. Registry 写路径扩展性 (7.5)：完全复现

`registry_scaling2`（median of 51）：

|--:|--:|--:|--:|--:|--:|

| 100 | 0.025 | 0.059 | 0.026 | 0.016 | 62% |

## 6. `/frame` vs `/frame.jpg` (4.2 / #14)：体积是恒等式，延迟幅度不可复现

原 harness 是两段各 50 次顺序采样，存在两个混入因素：两段屏幕内容随时间漂移、n=50 时
p95 取到第 48 个样本。我改成 **n=300、背靠背成对、交替先后顺序**。

| 端点 | p50 | p95 | 中位体积 |
|:--|--:|--:|--:|
| `/frame`（base64 JSON） | 0.673 ms | 1.071 ms | 104.0 KB |
| `/frame.jpg`（raw binary） | 0.618 ms | 0.929 ms | 77.9 KB |

- **体积：104.0 → 77.9 KB = −25.08%**（文档 −25.2%）
  但 `raw × 4/3 = 103.9 KB`，实测 104.0 KB（JSON 包装 +113 B）——**这就是 base64 的
  4/3 膨胀恒等式**。它不是"实测发现的收益"，而是"去掉 base64 层必然省 25%"的算术结论，
  与分辨率、内容、编码质量都无关。文档把它列进"实测净收益"一栏会让人误以为是可争取的优化空间。
  真正有信息量的表达是带宽绝对值：**2.90 MB/s → 2.18 MB/s @28.6 Hz**。
- **延迟：方向对、机制对、幅度不可复现。**
  - 成对差值 `t_b64 − t_raw`：中位 **+0.203 ms**，均值 +0.075 ms，标准差 **0.355 ms**
  - `raw` 更快的轮次占比 **50.7%**——和抛硬币没有区别
  - p95 差值 1.071 → 0.929 ms = 0.142 ms，**小于标准差**
  - 文档的 "p95 降 21.2%"（1.37 → 1.08）在我的测量中不成立

  > 有意思的是，成对差值中位数 +0.203 ms **恰好等于上一轮实测的 base64 编码成本 0.201 ms**——
  > 机制完全对得上。问题是这个量级（0.2 ms）被 HTTP/定时器噪声（σ=0.355 ms）完全淹没，
  > 用 n=50 的非配对采样报告 "-21.2%" 是把噪声当信号。

**结论**：`/frame.jpg` 值得用（省 25% 流量是确定的，服务端也少一次 base64 + 序列化），
但**不要用延迟百分比作为论据**；重启后 `ETag / 304` 才是带宽上的量级杠杆（静止时趋近 0）。

## 7. 新增内容里两处需要修正的技术判断

### 7.1 "耗时结论（编码/哈希）可跨内容套用" —— 对编码不成立（9.4 节）

同一分辨率（2560x1600, JPEG q80），夹具 vs 真实屏幕：

| 内容 | JPEG 编码 | JPEG 字节数 | 检测 | SoM 管线 | 管线产物 B64 |
|:--|--:|--:|--:|--:|--:|
| 合成高熵夹具 | **51.00 ms** | 2,863,315 B | 9.57 ms | **65.35 ms** | 3287 KB |
| 真实屏幕内容 | **22.22 ms** | 322,995 B | 10.78 ms | **36.26 ms** | 544 KB |

- 码流：夹具高估 **8.9x** → 文档"码流相关结论应以真实内容为准"✅
- 耗时：编码高估 **2.3x** → 文档"耗时结论（编码/哈希）可跨内容套用"**❌**
  - 哈希（FNV，逐字节算术）与内容无关 ✅
  - 边缘检测基本无关（9.57 vs 10.78 ms）✅
  - **JPEG 编码强相关**：高频噪声的 DCT 系数更多，编码更慢
- 因此 7.1 的 "2.5K 端到端 65.4 ms"、7 节的 "55.4 ms/次调用" 都是**夹具上界**，
  真实桌面的对应值是 **36.3 ms / 22.2 ms**。

> 文档 9.4 已自行标注了码流侧的差异，但没标注耗时侧；建议把这句改成
> "耗时结论中，哈希与检测可跨内容套用；**JPEG 编码不可**，实测差 2.3x"。

### 7.2 "上限 1920 或 1280 可省 28–42 ms"（7 节 P2-A）—— 1920 档完全不成立

文档的 55.4 / 27.5 / 13.8 ms 三行来自 `screenshot_cost.rs`，而那三张图是
**各自按目标尺寸生成的**（`fixture(w, h)`），**不含降采样成本**。真实路径要先
`process_dynamic_image` 缩放。加上这一段（`screen.rs:333-352`，RGBA + Triangle 多抽头）：

| max_dim | 缩放 | 编码(夹具) | **合计(夹具)** | 编码(真实) | **合计(真实)** |
|:--|--:|--:|--:|--:|--:|
| None | 0.25 ms | 50.28 ms | **51.04 ms** | 21.42 ms | **22.14 ms** |
| 1920 | **23.56** | 26.70 | **50.53 ms** | 12.30 | **35.96 ms** |
| 1280 | 11.74 | 12.14 | **24.00 ms** | 5.48 | **17.40 ms** |
| 960 | 10.50 | 6.80 | **17.37 ms** | 3.07 | **13.72 ms** |

- **1920 档**：夹具上 51.0 → 50.5 ms（**零收益**，缩放 23.6 ms 恰好抵消编码省下的 23.6 ms）；
  真实内容上 22.1 → 36.0 ms（**负收益，慢 13.8 ms**）
- **1280 档**：夹具省 27.0 ms（不是 42）；真实内容只省 **4.7 ms**
- 文档说的"省 28–42 ms"是把 55.4 减去 27.5 / 13.8 得到的，**漏掉了缩放这一段**

**但降采样仍然值得做——理由不是耗时，是体积**：

| max_dim | 真实内容 B64 体积 |
|:--|--:|
| None | 348 KB |
| 1280 | **100 KB** |
| 960 | **62 KB** |

3.5x 的产物体积削减，对一个要把截图塞进上下文窗口的 agent 来说比 5 ms 重要得多。
另外缩放本身可以变便宜：当前是在 **RGBA** 上做 Triangle 多抽头（11.7–23.6 ms），
先 `to_rgb8()` 再缩放、或改用盒式/最近邻，可把这段砍到 1/5 左右。

## 8. 复测方法与限制

- 所有 Rust 测量均为 release + `std::hint::black_box`，取中位数；端到端项用真实
  `target/release/at-pc-server` 与 `at-pc-agent --headless`（二进制比全部源文件新，非陈旧产物）
- 工装全部位于仓库外 `/tmp/atpc-perf/`，通过 path 依赖指向 `crates/agent`、
  `crates/server`、`crates/protocol`；**未修改仓库任何文件**
- 限制：
  1. 全部为 macOS 单机；Windows 的 `capture_active_window_state` 走
     `win_impl`（Win32 API），第 1 节的归因与方案不适用
  2. 第 1 节的绝对值随在屏窗口数变化（本次 7–14 窗）
  3. 第 7 节的"真实屏幕内容"取自本机当前桌面（IDE 场景），不同工作负载下
     JPEG 编码耗时会在 22–40 ms 区间浮动；但"夹具 ≠ 真实"这个**方向**是稳定的
  4. 第 6 节的 `/frame` 延迟差在 0.2 ms 量级、噪声 σ=0.355 ms，任何单次测量都无法给出
     可靠的百分比；如需定论应改用服务端内部计时（handler 入口到返回）而非 HTTP 往返
