## 1. 【最高收益】分块脏检：为省 CPU 而引入的、现在最大的 CPU 开销

### 1.1 实测：比基准所测函数慢 240 倍

`compute_block_hashes`（`desktop-core/src/lib.rs:89`）对每个 64×64 块做**逐字节** FNV-1a——
即每帧把**全部像素**过一遍哈希，而不是抽样。实测（本机 macOS/aarch64，release，`black_box` 保护）：

| 分辨率 | 帧字节数 | 块数 | `compute_sample_hash`（基准所测） | `compute_block_hashes`（生产所用） | 倍数 | 有效吞吐 |
|:---|---:|---:|---:|---:|---:|---:|
| 1280x720 | 3.7 MB | 240 | 0.013 ms | **3.606 ms** | **276x** | 1.02 GB/s |
| 1920x1080 | 8.3 MB | 510 | 0.033 ms | **8.035 ms** | **241x** | 1.03 GB/s |
| 2560x1600 | 16.4 MB | 1000 | 0.066 ms | **16.083 ms** | **245x** | 1.02 GB/s |
| 3840x2160 | 33.2 MB | 2040 | 0.316 ms | **31.933 ms** | **101x** | 1.04 GB/s |

**根因不是内存带宽**：现代核心可流式读取 20–50 GB/s，而实测只有 **~1 GB/s**。FNV-1a 每字节是
`hash = hash * P ^ b`，**逐字节串行依赖**，无法向量化也无法流水化（乘法延迟 3–5 cycle 直接串起来）。
即使 510 个块之间彼此独立、乱序引擎可以重叠，实测仍只到 1 GB/s 量级。

### 1.2 它在整帧预算中的位置

阶段归因（合成的等熵夹具，与仓库基准同源）：

| 阶段 | 1920x1080 → 1280x720 | 2560x1600 → 1280x800 |
|:---|---:|---:|
| **脏检（哈希 + 比较）** | **7.844 ms** | **15.737 ms** |
| RGBA → RGB（缩放） | 0.571 ms | 0.648 ms |
| JPEG 编码 q55 | 10.431 ms | 10.679 ms |
| 空闲帧（仅脏检，不编码） | 7.834 ms | 15.640 ms |
| 活跃帧（脏检+转换+编码） | 18.845 ms | 27.064 ms |
| 单核 fps 上限 | 53.1 | 36.9 |

> 在 2560x1600 上，**脏检（15.7 ms）比它要避免的 JPEG 编码（10.7 ms）还贵 47%**。

### 1.3 端到端验证：真实进程、真实屏幕

起真实 `at-pc-server` + `at-pc-agent --headless`（显示 2560x1600 / scale 1.0），用 `ps -o time=` 累计 CPU 时间差分测 Agent 进程：

**基线**：注册在线但不推流 → **0.0% 核心**（12 s 内 CPU 时间无变化）。

**开推流后按帧率扫描**（每档 8 s）：

| fps 设置 | CPU 秒/8s | 占单核 | 每探测 CPU |
|---:|---:|---:|---:|
| 1 | 0.24 | 3.0% | 30.00 ms |
| 3 | 0.70 | 8.7% | 29.17 ms |
| 6 | 1.32 | 16.5% | 27.50 ms |
| 9 | 1.76 | 22.0% | 24.44 ms |
| 12 | 2.18 | 27.2% | 22.71 ms |
| **15（前端默认）** | **2.59** | **32.4%** | 21.58 ms |
| 20 | 3.04 | 38.0% | 19.00 ms |
| 25 | 2.95 | 36.9% | — |
| 30 | 2.94 | 36.7% | — |

**三个关键读数**：

1. **静态桌面下 12 s 只产出 0.7 帧/s，却持续消耗 31.8% 核心。**
   帧没送出去，CPU 一分没省——因为抓屏和脏检在判定之前都照跑了。
2. **CPU 在 20–25 fps 之间饱和于 ~38% 核心**，此后加帧率不再涨。说明循环被**单次探测的墙钟延迟**（而非 CPU）卡住，真实上限约 **20–22 次探测/s**，而不是所请求的 30 fps。
3. 每探测 CPU ≈ 21.6 ms（空闲）～30 ms（脏帧），其中**哈希 15.6 ms 占空闲探测的 72%**（2560x1600 实测值）。

### 1.4 为什么这么多轮门禁都没抓到

- **三个基准文件全部仍测旧哈希**：`p1_hot_paths.rs:59`、`p2_perf_deep.rs:62/84`、`perf_probe.rs:101/137/170` 调用的都是 `compute_sample_hash`；而 `grep compute_block_hashes crates/ --include=*.rs` 的结果只有 **`stream.rs:249` 一处调用点**（其余是测试）。也就是说 `PERFORMANCE.md` 里"P1-7 基线 ↔ P1-3 对比"所比的是**生产已经不再走的路径**。
- 基准输出因此写着 `dirty-check hash 0.000 ms (0.0%)` / `JPEG encode 97.1%`——**结论已经反了**：2560x1600 上脏检应占约 37% 的活跃帧预算。
- **CI 无性能门禁**：`grep -rn "bench|criterion|threshold" .github/` 为空。`thresholds.toml` 存在但没有任何自动化引用。CI 只做 `bench --no-run`（编译），因此一次 240 倍的哈希替换可以全绿通过。
- 计划文档中 P1-3 已标注"✅ 已验收"，验收描述里明确写了"64×64 块哈希 + 0.5% 脏块比"——**设计被验收了，成本从未被测量**。

### 1.5 方案：同语义、零风险、14 倍

`desktop-core` 是纯函数 crate，替换哈希实现不动任何契约。原型（word-wise：8 字节一组，`hash.rotate_left(13) ^ word.wrapping_mul(0x9e3779b97f4a7c15)`，尾部不足 8 字节落回逐字节）：

| 分辨率 | 生产实现 | 词宽原型 | 提速 | 1/4 步长原型 | 提速 |
|:---|---:|---:|---:|---:|---:|
| 1920x1080 | 7.854 ms | **0.559 ms** | **14.1x** | 1.964 ms | 4.0x |
| 2560x1600 | 15.645 ms | **1.299 ms** | **12.0x** | 4.127 ms | 3.8x |

**检测行为完全一致**（同一夹具、同一块网格、64 次随机位置各测）：

| 变化 | 生产 | 词宽原型 | 1/4 步长原型 |
|:---|---:|---:|---:|
| 文本光标 2x18 | 100.0% | 100.0% | 100.0% |
| 单个字形 8x16 | 100.0% | 100.0% | 100.0% |
| 时钟数字 10x16 | 100.0% | 100.0% | 100.0% |
| 鼠标指针 32x32 | 100.0% | 100.0% | 100.0% |

词宽原型不只是"实测一致"，性质上也保底：块内任意单字节改动必然落在某个 8 字节字组里，
而 `h ← rot(h,13) ^ (w*C)` 对 `w` 是**双射**（C 为奇数，乘法可逆；循环移位与异或均为双射），
因此**任意单字节改动必然改变该块哈希**；多字组改动仅存在 ~2⁻⁶⁴ 量级的碰撞概率。
换句话说：**检测能力不退，成本退 14 倍**。

**预期收益**（2560x1600，按实测外推）：

| 指标 | 当前 | 替换后 | 变化 |
|:---|---:|---:|---:|
| 空闲探测 CPU | 21.6 ms | ~7.1 ms | **-67%** |
| 15 fps 静态桌面占用 | 32.4% 核心 | ~11% 核心 | **-66%** |
| 脏帧探测 CPU | ~30 ms | ~15.4 ms | -49% |
| 活跃帧预算 | 27.06 ms | 12.7 ms | -53%（单核 fps 上限 36.9 → 78.5） |

**风险**：低。唯一需要同步的是重建基准——把 `compute_block_hashes` 纳入基准与阈值，
否则这次替换同样无法被验收（见 P1-2）。

## 2. 抓屏仍排在判定之前：静态画面的空转没有被消除

第一轮报告的头号 P0 至今未落地。当前循环顺序（`stream.rs:243-256`）：

```
spawn_blocking {
    capture_image()                      // ① 无条件抓屏（最贵的一步）
    compute_block_hashes(...)            // ② 全帧哈希（第二贵）
    decide_frame_send(...)               // ③ 现在才判断要不要发
}
```

端到端证据：12 s 静态桌面只产出 0.7 帧/s，Agent 仍持续吃 31.8% 核心。按实测分解，
其中约 **26 ms/次是抓屏**（墙钟 ~31 ms 中大部分是等待而非计算），**15.6 ms/次是哈希**。

**方案（按性价比排序）**

1. **空闲退避**：连续 K 帧（3–5）判定为静止后，把探测频率降到 1–2 Hz，一旦发现变化立即恢复。
   静止场景 15 → 1–2 次/s，开销从 ~32% 降到 **~2–4% 核心**（哈希替换后可再降到 <1%）。
   延迟代价与当前 5 s keepalive 上限同量级，不构成新的体感回归。
2. **平台级变更通知**（中期）：macOS `CGDisplayStream` / Windows DXGI Desktop Duplication 提供
   dirty rect 或帧到达回调，把"是否需要抓屏"前置到平台层。这是唯一能把抓屏等待也一起省掉的路径，
   但工作量显著更大，建议单独立项做可行性验证。
3. **本轮即可做的小改动**：把 `should_send_frame` 的 keepalive 判定挪到抓屏之前（用上次已知状态）。

## 3. 小改动被"检出但丢弃"：阈值与 keepalive 的相互作用

P1-3 把检测率从 4.7%–51.6% 拉到了 **100%**（这一项是真实改进，值得肯定）。
但检测之后的处置把它抵消了：

```
判定：dirty_block_ratio >= 0.005   → 0.5% × 510 块 = 2.55 块，即 1080p 上必须 ≥3 块变化
```

实测（1920x1080，阈值 2.55 块）：

| 变化 | 脏块数 | 脏块比 | 判定 |
|:---|---:|---:|:---|
| 文本光标 2x18 | 2 | 0.00392 | **Skip** |
| 时钟数字 10x16 | 2 | 0.00392 | **Skip** |
| 任务栏角标 16x16 | 2 | 0.00392 | **Skip** |
| 鼠标指针 32x32 | 2 | 0.00392 | **Skip** |
| 两个 64×64 块（相距） | 4 | 0.00784 | Encode |
| 大指针 96x96 | 6 | 0.01176 | Encode |
| 窗口区域 400x200 | 28 | 0.05490 | Encode |
| 全宽横条 1920x8 | 30 | 0.05882 | Encode |

而 `STREAM_KEEPALIVE_INTERVAL` 已从 HEAD 的 **1000 ms 放宽到 5000 ms**
（`git show HEAD:crates/agent/src/stream.rs` 第 160 行 `Duration::from_millis(1000)` ↔
`desktop-core/src/lib.rs:162` `Duration::from_secs(5)`）。

**净效果**：打字时单个字符/光标闪烁、时钟跳秒这类"小于约 2 个块"的变化，
在远端最长 **5 秒**不刷新——比改动前的 1 秒**更差**。检测能力提升 100%，
但用户可见的时延反而增加 5 倍。

**方案**：把 keepalive 收紧到 250–500 ms（成本很低：空载保活帧是 header-only，无 JPEG），
或对"变化面积小但确实变化"的情况走一条轻量通道（只发脏块矩形，不重编全帧）。
两者都建议与第 1 节的退避机制联动调参——退避决定了"多久探测一次"，keepalive 决定了"多久兜底一次"。

## 4. 服务端投递：每次轮询重算 base64（第一轮 P1 未落地）

`router.rs:754-762` 仍是原样：

```rust
let frames = self.desktop_frames.read().unwrap();          // std RwLock 读锁
let mut frame = frames.get(terminal_id).cloned()?;
if frame.data.is_empty() && !frame.raw_bytes.is_empty() {
    frame.data = BASE64_STANDARD.encode(&frame.raw_bytes);  // 读锁内做 CPU 密集工作
}
```

帧入库点（`router.rs:852-863`）写的是 `data: String::new()` + `raw_bytes`，因此**每次轮询必然重算一次**。

用仓库自带探针在本机实测（当前代码）：

| 阶段 | 实测 |
|:---|---:|
| frame clone（`Vec<u8>`） | 0.010 ms |
| base64 编码 | 0.201 ms |
| **生产 accessor（clone + base64）** | **0.198 ms** |
| **生产 raw accessor（仅 clone）** | **0.010 ms** |
| `serde_json` body 序列化 | 0.304 ms |
| 单次轮询合计 | 0.501 ms |

前端 `session.js:549` 是 `setTimeout(r, 35)` → **28.6 次轮询/s**，而流是 15 fps：

| 观看者 | 服务端串行开销 | 线上流量（合成 1080p 夹具） |
|---:|---:|---:|
| 1 | 14.3 ms/s（1.43% 核） | 31.8 MB/s |
| 3 | 0.04 核 | 95 MB/s |
| 5 | 0.07 核 | 159 MB/s |

> ⚠️ 上表流量一列用的是**高熵合成夹具**码流，严重高估。同一量纲下的真实内容是
> **2.90 MB/s @28.6 Hz**（见 4.2 节实测），低一个数量级。服务端 CPU 一列（仅 clone + base64）
> 与内容无关，可继续引用。

**方案**：在**帧入库时**一次性算好 base64 随缓存存放（改 `router.rs:852`），读取路径只 clone；
或直接采用已存在的 `get_latest_desktop_frame_raw`（0.010 ms，快 19.8 倍）配合前端原生解码。

### 4.2 真实 Server + Agent 端到端实测对比（**已按 n=300 成对复测修正**）

初稿用两段各 50 次**顺序采样**，存在两个混入因素：两段屏幕内容随时间漂移、n=50 时 p95 取到第 48 个样本。
改为 **n=300、背靠背成对、交替先后顺序**后：

| 端点 | p50 | p95 | 中位体积 |
|:---|---:|---:|---:|
| `/frame`（base64 JSON） | 0.673 ms | 1.071 ms | 104.0 KB |
| `/frame.jpg`（raw binary） | 0.618 ms | 0.929 ms | 77.9 KB |

**① 体积：数值对，但性质被写错了。**

104.0 → 77.9 KB = **−25.08%**（初稿 −25.2%，一致）。但 `raw × 4/3 = 103.9 KB`，实测 104.0 KB
（JSON 包装 +113 B）——**这就是 base64 的 4/3 膨胀恒等式**，不是"实测发现的优化空间"：
只要去掉 base64 层就必然省 25%，与分辨率、内容、编码质量都无关。把它列进"实测净收益"一栏，
会让人误以为那是可争取的优化空间。有信息量的表达是带宽绝对值：**2.90 MB/s → 2.18 MB/s @28.6 Hz**。

**② 延迟：方向对、机制对，但幅度不可复现，不能作为论据。**

| 指标 | 初稿（n=50 顺序） | 复测（n=300 成对） |
|:---|---:|---:|
| p50 差 | −6.2% | 中位差 **+0.203 ms**（raw 反而更慢） |
| p95 差 | −21.2% | 1.071 → 0.929 = 0.142 ms，**小于标准差** |
| raw 更快的轮次 | — | **50.7%**（与抛硬币无区别） |
| 成对差值分布 | — | 中位 +0.203 ms、均值 +0.075 ms、**σ = 0.355 ms** |

成对差值中位数 +0.203 ms **恰好等于上一轮实测的 base64 编码成本 0.201 ms**——机制完全对得上。
问题是这个量级被 HTTP / 定时器噪声（σ = 0.355 ms）完全淹没。初稿用 n=50 的非配对采样报告
"−21.2%"，是**把噪声当信号**。

**结论**：`/frame.jpg` 值得用（省 25% 流量是确定的，服务端也少一次 base64 + JSON 序列化），
但**不要用延迟百分比作为论据**；`ETag / 304 Not Modified` 才是带宽上的量级杠杆（桌面静止时趋近 0）。

### 7.4 list_processes：**结论对，归因与方案已修正**

| 项 | 初稿 | 独立复测 |
|:---|---:|---:|

| 参考实现：refresh + 先过滤再物化 | 未测 | 2.26 ms |

结论"**过滤不省时**"✅——`process.rs:54-55` 确实在 `filter` 匹配之前，先对全系统所有进程

**但量级判断错了**：

- 全量物化 − 过滤物化 = 2.65 − 2.68 = **0.03 ms**

机制确认：`meta_store.rs:216-221` 的 `snapshot_locked` 在写锁内做 `state.records.clone()`，
**占单次写成本的 62–66%**；`register` / `update_meta` / `remove` 每次都走一遍。✅

## 9. 未覆盖与后续验证

1. **Windows / Linux 抓屏路径**：本轮全部在 macOS 实测。Windows 走 DXGI Duplication，
   其抓屏成本、抖动特性与 CPU/等待比例可能完全不同，第 2、3 节的结论需在 Windows 上重验。
   **7.2 节的归因与方案仅适用 macOS**——Windows 走 `win_impl`（Win32 API），
   不涉及 xcap 窗口枚举那 82% 的成本，直连 `CGWindowListCopyWindowInfo` 的结论也不适用。
2. **HiDPI 缩放因子**：本机为 `scale 1.0`。Retina 下 `capture_image()` 返回逻辑尺寸还是物理像素，
   会直接改变哈希的输入字节数与第 1 节的绝对耗时。
3. **多显示器**：本轮只测主屏；`find_monitor` 在切换显示器时会重置缓存的 Monitor 句柄。
4. **哈希输入与真实屏幕内容的耦合 —— ⚠️ 初稿判断部分不成立，已修正**：
   本报告多处使用高熵合成夹具。实测同分辨率（2560x1600, JPEG q80）夹具 vs 真实屏幕：

   | 内容 | JPEG 编码 | JPEG 字节数 | 边缘检测 | SoM 管线 | 管线产物 B64 |
   |:---|---:|---:|---:|---:|---:|
   | 合成高熵夹具 | **51.00 ms** | 2,863,315 B | 9.57 ms | **65.35 ms** | 3,287 KB |
   | 真实屏幕内容 | **22.22 ms** | 322,995 B | 10.78 ms | **36.26 ms** | 544 KB |

   - **码流**：夹具高估 **8.9x** → 初稿"码流相关结论（带宽）应以真实内容为准" ✅
   - **耗时**：初稿称"耗时结论（编码/哈希）可跨内容套用" —— **对 JPEG 编码不成立** ❌
     编码高估 **2.3x**（高频噪声的 DCT 系数更多、编码更慢）；
     哈希（FNV，逐字节算术）与边缘检测（9.57 vs 10.78 ms）确实与内容无关 ✅
   - 因此第 7 节的 "55.4 ms/次调用"、7.1 的 "65.4 ms / 3.29 MB" 都是**夹具上界**，
     真实桌面对应值是 **22.2 ms / 36.3 ms / 544 KB**。引用时必须注明。

5. **7.2 节的绝对值随环境变化**：`capture_active_window_state()` 的耗时随**在屏窗口数**增长
   （本次 7 窗 20.30 ms / 14 窗 21.39 ms）。写"14.73 ms"或"21 ms"而不附窗口数即不可复现。

6. **`/frame` vs `/frame.jpg` 的延迟差无法用 HTTP 往返定量**：差值在 0.2 ms 量级、
   噪声 σ = 0.355 ms，任何单次或小样本测量都给不出可靠百分比。
   如需定论应改用**服务端内部计时**（handler 入口到返回），而非 HTTP 往返。
   跨机器直接套用绝对值请谨慎（见第 7 条）。
7. **端到端交互延迟**：本轮已实测了 Server+Agent 之间的流式帧传输（`/frame` vs `/frame.jpg`）与 MouseMove 输入吞吐，但完整的闭环链路（前端浏览器 UI 事件监听 → 网络 → 服务端注入生效 → OS 窗口合成 → 抓屏像素回流 → 前端 Canvas 渲染）仍受前端宿主环境依赖影响，有待搭建浏览器端打点完成全链路端到端延迟测定。
8. 本报告所有绝对值均为单机测量，用于比较方案的**相对增益**可靠；跨机器直接套用绝对值请谨慎。

## 10. 一句话总结

> P1-3 把"漏检"修好了（检测率 4.7%–51.6% → 100%），但**代价是把脏检从 0.033 ms 的抽样哈希
> 换成了 16 ms 的全帧逐字节哈希**——在 2560x1600 上它比它所要避免的 JPEG 编码还贵，
> 占流式 CPU 的约 72%。而这个 240 倍的替换**通过了全部门禁**，因为基准测的是已被弃用的旧函数、
> CI 没有任何性能门禁。同语义的 8 字节分组哈希可拿回 **14 倍**，且检测行为实测完全一致；
> 叠加"抓屏前置 + 空闲退避"后可把静态场景的 Agent CPU 从 **32% 降到个位数**。
> 这两件事都属于"低风险、可立即做"的范畴，而它们之所以还没做，是因为**没人度量**。

**第二轮补充内容（第 11–14 项、4.2、7.1–7.5）经独立复测后的净结论**：数据层 4 项精确复现
（SoM 产物体积逐字节一致、MouseMove 268.9 字节/条、Registry 逐档吻合），
但 **2 处归因方向反了、1 处幅度站不住、1 条性质写错**：

- 动作审查贵的不是进程扫描（11%），是 **xcap 窗口枚举（82%）**——正解是直连
  `CGWindowListCopyWindowInfo`（21.4 → 0.14 ms），而非"免进程扫描"（只省 2.4 ms）
- `list_processes` 贵的不是堆克隆（4%），是**每次调用的 `refresh_processes()`（96%）**——
  正解是 TTL 缓存，而非"过滤前置"
- `/frame.jpg` 的 −25% 流量是 **base64 的 4/3 恒等式**，不是优化空间；
  其"p95 延迟 −21.2%"在 n=300 成对复测下**完全落在噪声内**（σ=0.355 ms）
- "设 1920 上限省 28–42 ms" **漏算了 23.6 ms 降采样**：1920 档零收益/负收益

> 一句话：**这轮补充的"是什么"基本都对，"为什么"错了两次，"能省多少"错了两处。**
> 数字本身可靠，归因与方案需要按本版修正重排。
