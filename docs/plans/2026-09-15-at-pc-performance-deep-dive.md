## 1. 核心结论速览

### 1.1 真实场景帧预算（2560x1600 → 策略缩放 1280x800，q55）

| 阶段 | 耗时 | 占帧预算 | 备注 |
|:---|---:|---:|:---|
| **抓屏 capture_image** | **21.58 ms** | **74.7%** | 抖动极大，实测 7–41 ms |
| RGBA→RGB 转换 | 1.59 ms | 5.5% | 有 4.8x 余量未用（§2.6） |
| JPEG 编码 q55 | 5.74 ms | 19.9% | 纯标量实现 |
| **合计** | **28.9 ms** | 100% | 单核 fps 上限 ≈ **34.6 fps** |

15 fps 目标预算为 66.7 ms，当前占用 43%。**但抓屏抖动会击穿它**：实测连续 5 帧抓屏为 `25.7 / 34.9 / 27.2 / 35.1 / 41.2 ms`，叠加 1080p 级编码（§2.2 的 20.1–23.3 ms）后单帧可达 60+ ms，**15 fps 目标贴边失守**。

### 1.2 静态画面的无效开销（最容易被忽视的一项）

`crates/agent/src/stream.rs` 的循环顺序是：**先抓屏（L96），再算哈希（L107），命中静止才跳过编码**。也就是说——

> 静止画面下，抓屏照常全速执行，只是编码成果被丢弃。

按实测推算：静止桌面 15 iters/s × 21.58 ms = **324 ms/s ≈ 单个核心的 32%**，持续空转。这是整个项目**单位收益最高的优化点**。

### 1.3 问题清单（按实测影响排序）

| # | 问题 | 实测证据 | 影响面 | 优先级 |
|:--|:---|:---|:---|:---|
| 1 | 去重检查在抓屏**之后** | 静止画面 324 ms/s ≈ 32% 核 | Agent CPU | **P0** |
| 2 | 1920 像素悬崖：`>1920` 才缩放 | 1920x1080 = 23.62 ms / 813.9 KB ↔ 1921x1080 = 6.74 ms / 281.8 KB | CPU + 带宽 | **P0** |
| 3 | 每次轮询重算 base64 | accessor 0.216 ms ↔ raw 0.010 ms（**21.6x**） | Server CPU + 分配 | **P0** |
| 4 | 轮询 28.6 Hz ≠ 出帧 15 Hz | 约 **48%** 轮询是重复的 | Server + 前端 + 带宽 | P1 |
| 5 | JPEG 编码占流水线 86.4% | 1080p q55：编码 20.1 ms / 总计 23.3 ms | Agent CPU | P1 |
| 6 | 采样去重精度 0.391% | 光标/时钟检出率 4.7%–14.1% → 最长 1 s 静止假象 | 视觉体验 | P1 |
| 7 | RGBA→RGB 有 4.83x 余量 | 3.084 ms → 0.639 ms，**输出字节等价** | Agent CPU | P1 |
| 8 | 多观看者无 raw 通道 | raw 端点省 33% 带宽 | 带宽 | P2 |
| 9 | 注册表全量快照克隆 | 5000 终端 0.716 ms/次 | 仅重连风暴时 | P2 |

### 1.4 实测排除的疑点（诚实清单）

以下项目在本次测量中**不是**瓶颈，不应排期：

| 项目 | 实测值 | 判断 |
|:---|:---|:---|
| 审计写入 | 0.0079 ms/条 → 28.6 事件/s 时 **0.226 ms/s（0.02% 核）** | 无需优化 |
| 审计 flush / 读取 | 0.0169 ms / `read_recent(100)` 0.1440 ms | 无需优化 |
| `BinaryDesktopFrame` 编解码 | 0.0005 ms（encode 与 decode 各） | 大端拷贝不是问题 |
| 采样哈希本身 | 33.8 µs（**0.0%** 帧预算） | 有巨大余量可用（§2.6 反向利用） |
| HTTP 单请求开销 | ~0.07 ms 中位数 | 可忽略；**请求数**比单请求成本重要 |
| 心跳更新元数据 | `update_heartbeat()` 只改内存 session，**不触达 meta_store** | 无 O(n²) |

## 2. 逐项深度分析

### 2.1 抓屏成本与"抓屏后才去重"（P0，最高收益）

**证据**

- `crates/agent/src/stream.rs:96` 抓屏 → `:107` `compute_sample_hash` → `:108` 才判断是否发送。
- 真实抓屏中位数 **20.95 ms**；两轮运行分别为 19.92 / 20.95 ms，连续采样跨度 **7.19 – 41.22 ms**。
- 静止画面下循环周期被 `frame_interval`（15 fps → 66 ms）卡住，仍在每周期抓一次屏：15 × 21.58 ms ≈ **324 ms/s**。

**影响**：持续占用约 1/3 个核心，纯粹用于产生随后被丢弃的帧。风扇、续航、以及与其他工具的 CPU 竞争都被这一项主导。它同时解释了为什么 §1.1 的帧预算在主机有负载时会失守。

**方案**

1. **空闲退避（推荐，改动最小）**：连续 K 帧（建议 3–5 帧）哈希未变即把探测频率降到 1–2 Hz，一旦发现变化立即恢复目标帧率。
   - 静止场景：15 → 1–2 次抓屏/s，开销从 324 ms/s 降至 **21–43 ms/s（约 10–15x 降幅）**。
   - 延迟代价：最长 0.5–1 s 才察觉变化——**与当前 1 s keepalive 的上限完全一致**，因此不构成回归。
2. **平台级变更通知（中期）**：macOS `CGDisplayStream` / Windows DXGI Desktop Duplication 可提供 dirty rect 或帧到达回调，把"是否需要抓屏"的判断前置到平台层，理论上可再降一个数量级。此项工作量显著更大，建议单独立项做可行性验证。
3. **顺序调整**：若保留当前语义，至少把 `should_send_frame` 的 keepalive 判定移到抓屏前（可利用上次已知状态），避免"刚超时即抓屏"的冗余。

**预期收益**：静止/低变化场景 Agent CPU 降低 **~90%**；不改变动态场景表现。

**风险**：低。退避窗口需与 keepalive 语义对齐，避免"变化检测延迟"被误判为卡顿。

### 2.2 1920 像素悬崖：最常见的分辨率得到最差的待遇（P0）

**证据**

缩放策略位于 `crates/desktop-core/src/lib.rs:15`：

```rust
if orig_w > 1920 {          // 仅看宽度，且严格大于
    let target_w = orig_w / 2;   // 最近邻点采样，2x 抽取
```

实测分辨率策略表（合成夹具，1080p 级）：

| 源分辨率 | 输出 | 是否缩放 | 转换 ms | 编码 ms | 合计 ms | fps_cap | JPEG KB |
|:---|:---|:---|---:|---:|---:|---:|---:|
| **1920x1080** | **1920x1080** | **否** | 3.34 | 20.28 | **23.62** | **42.3** | **813.9** |
| 1921x1080 | 960x540 | 减半 | 0.78 | 5.96 | 6.74 | 148.3 | 281.8 |
| 2560x1440 | 1280x720 | 减半 | 1.47 | 10.14 | 11.61 | 86.1 | 499.2 |
| 3840x2160 | 1920x1080 | 减半 | 3.27 | 23.23 | 26.50 | 37.7 | 1123.0 |

criterion 交叉验证：`frame/pipeline_full/1920x1080 = 27.66 ms` 而 `2560x1440 = 11.59 ms`——**逻辑分辨率更小的屏幕反而慢 2.4 倍**。

根因：1920x1080 在 `>1920` 判定下"恰好不触发"，于是编码 2.07 Mpx；1921 宽的屏幕只编码 0.52 Mpx。**4 倍像素差**，换算成实测比值是 **3.5x 时间 / 2.9x 码流**。而 1920x1080 正是最主流的桌面分辨率。

**方案**：把阈值判据从"宽度 > 1920"改为**输出像素上限**——例如 `max_output_pixels = 1_150_000`（≈1280x900）或 `max_output_width = 1600`，统一按比例缩放并取整到偶数。这样 1920x1080 → 约 1280x720，与 1921 行现状对齐。

**预期收益**：1920x1080 用户时间 **-72%**（23.62 → 6.74 ms）、码流 **-65%**（813.9 → 281.8 KB）。零新增依赖、单点改动，可直接沿用现有 nearest-neighbor 路径（甚至不改缩放算法）。

**风险**：低。唯一需确认的是"1920x1080 是否要保留原分辨率以保文本清晰度"这一产品取舍；若需要，可对 1920 恰好命中时改用 `2:1` 之外的轻缩放（如 0.75x）折中。**次要点**：当前用最近邻点采样（`x*2, y*2`）降采样会产生明显锯齿，屏幕文本尤其受损；若改为 2x2 盒式平均，画质提升但转换耗时上升（可用 §2.6 省下的余量支付）。

### 2.3 每次轮询重算 base64（P0）

**证据**（`crates/server/src/router.rs:754-762`）

```rust
pub async fn get_latest_desktop_frame(&self, terminal_id: &str) -> Option<DesktopFrameCache> {
    let frames = self.desktop_frames.read().unwrap();     // 持 std RwLock 读锁
    let mut frame = frames.get(terminal_id).cloned()?;
    if frame.data.is_empty() && !frame.raw_bytes.is_empty() {
        frame.data = base64::prelude::BASE64_STANDARD.encode(&frame.raw_bytes);   // CPU 密集
    }
    Some(frame)
}
```

实测投递分解：

| 项目 | 实测 |
|:---|---:|
| frame clone（`Vec<u8>`） | 0.010 ms |
| base64 编码 | 0.202 ms |
| **生产 accessor（clone + base64）** | **0.216 ms** |
| **生产 raw accessor（仅 clone）** | **0.010 ms** |
| `serde_json` body 序列化 | 0.313 ms |
| **单次轮询合计** | **0.529 ms** |

帧缓存写入点（`router.rs:834`）把 JPEG 存进 `raw_bytes` 且 `data` 为空，所以**每次轮询都会重算一次 base64**，且在 `std::sync::RwLock` 读锁内同步执行。

**问题有两层**：

1. **重复计算**：同一帧被 N 个观看者、以 28.6 Hz 的节奏反复编码。accessor 成本是 raw 的 **21.6 倍**。
2. **锁内做 CPU 密集工作**：`std::sync::RwLock` 读锁 + 0.202 ms 的编码，会阻塞帧缓存写入方。

**方案**：在**帧入库时**一次性计算 base64 并随缓存存放（写入点 `router.rs:834`），读取路径只做 clone。等效于把 accessor 从 0.216 ms 降到 0.010 ms。若进一步改用 raw 二进制端点（§2.7），则连 base64 都不必产生。

**预期收益**：每观看者服务端序列化开销 **15.1 ms/s → 约 3 ms/s**（降 ~80%）；同时消除"读锁内 0.2 ms 阻塞写"的问题。

**风险**：低。需注意缓存内存占用增加 33%（base64 展开），可用"按需双缓存 + LRU"或直接采用 raw 端点规避。

### 2.4 轮询频率与出帧频率不匹配（P1）

**证据**

- 前端 `crates/server/frontend/index.html:2074`：`setTimeout(r, 35)` → **28.6 次轮询/s**。
- 前端启动参数（`:1902`）：`{ fps: 15, quality: 55 }` → 出帧 **15 fps**。

**28.6 / 15 ≈ 1.9**，即约 **48% 的轮询拿到的是同一帧**。`index.html:2047` 用 `data.timestamp !== lastTimestamp` 跳过了图片解码，但**跳不过 HTTP、`res.json()` 对 1.1 MB body 的解析、以及 base64 字符串的物化**。服务端侧同样全量付出。

**方案**：把"拉"改成"推"——服务端已有 WS 基础设施，可把 JPEG 二进制帧直接推给浏览器；或退一步用长轮询 / `ETag` + 304 让无变化时几乎零成本。

**预期收益**：消除约 48% 的空轮询（服务端序列化、前端 JSON 解析、网络往返同步下降），并顺带消掉 35 ms 定时器带来的出帧抖动。

**风险**：中。需要前端渲染循环改造，并处理 WS 重连与背压。建议与 §2.7 一并实施（两者都指向"用二进制 WS 替代 HTTP+base64+JSON"）。

### 2.5 JPEG 编码：占流水线 86.4%（P1）

**证据**（1080p，q55）

| 阶段 | 耗时 | 占比 |
|:---|---:|---:|
| 脏帧哈希 | 0.000 ms | 0.0% |
| RGBA→RGB | 3.171 ms | 13.6% |
| **JPEG 编码** | **20.112 ms** | **86.4%** |
| 合计 | 23.283 ms | 100% |

编码器为 `image` crate 的 `JpegEncoder`（`crates/desktop-core/src/lib.rs:72`），**纯 Rust 标量实现**（依赖树中的 `zune-jpeg` 只用于解码）。

质量曲线（1080p）：

| 质量 | 编码 ms | 相对 q55 |
|:---|---:|---:|
| q40 | 17.74 | -12% |
| **q55** | **20.09** | 基准 |
| q70 | 24.82 | +24% |
| q85 | 33.61 | +67% |
| q95 | 48.67 | +142% |

**方案（按推荐顺序）**

1. **先做 §2.2（减像素）**——减少 75% 像素直接等比削减编码时间，收益立竿见影且零依赖风险。
2. **再评估 SIMD 编码器**：libjpeg-turbo（`turbojpeg`）或 mozjpeg 绑定通常比标量实现快数倍，但会引入 C 构建依赖，需在目标平台（含 Windows）实测后才能定论。**本报告不宣称具体倍数**——请以自建基准为准。
3. **质量档位即策略**：q85 → q55 可省 40% 编码时间，当前前端默认 55、上限被 `quality.min(85)` 钳制（`stream.rs:67`），这部分已合理。

**预期收益**：与 §2.2 叠加，1080p 无缩放路径编码成本有望从 ~20 ms 降到个位数毫秒。

**风险**：中（引入 C 依赖会影响跨平台构建链）；建议先落地 1、3，把 2 作为独立实验项。

### 2.6 采样去重的精度与"免费"的提升空间（P1）

**证据**（`crates/desktop-core/src/lib.rs:48-56`）

```rust
for chunk in raw_rgba.chunks(256) {
    if let Some(&byte) = chunk.first() { /* FNV */ }
}
```

每 256 字节取 1 字节，即 **每 64 个像素只取 1 个像素的 R 通道**，采样密度 **0.391%**。

| 变化类型 | 检出率 | 后果 |
|:---|---:|:---|
| 文本光标 2x18 | **4.7%** | 打字时光标最长 1 s 不刷新 |
| 时钟数字 10x16 | **14.1%** | 秒数跳变常被吞掉 |
| 任务栏角标 16x16 | 26.6% | 通知闪烁延迟 |
| 光标 32x32 | 51.6% | 偶发迟滞 |
| 窗口区域 400x200 | 100.0% | 正常 |

`should_send_frame` 的兜底是 **1 s keepalive**（`stream.rs:112`），因此"漏检"的最坏表现是**画面以 1 Hz 刷新**——用户在打字、看进度条、观看滚动时会看到明显卡顿感。

**方案**：提高采样密度。当前哈希只占帧预算的 **0.0%**（33.8 µs），有 **1–2 ms 的预算可以花**（仍不到帧预算的 10%）。
- 把密度从 1/256 提到 1/16（每 4 像素取 1）→ 约 0.55 ms，检出率提升约 16 倍。
- 或对全帧做 xxhash/CRC32（全帧读 ~8.3 MB）→ 约 1–2 ms，得到精确的脏帧判定。
- 同时把 keepalive 从 1 s 收紧到 250–300 ms 作为兜底。

**预期收益**：动态内容刷新从 1 Hz 恢复到实时；用已有余量支付，不挤占编码预算。

**风险**：低。需在"提高灵敏度"与"增加编码次数"之间平衡——密度过高会让"聊天窗口光标闪烁"这类真实变化也触发全帧编码，反而增加 CPU。建议配合 §2.1 的退避机制（静态→低频探测）联动调参。

### 2.7 传输形态：raw 二进制与多观看者放大（P2）

**证据**

| 指标 | 当前（JSON + base64） | raw 端点 |
|:---|---:|---:|
| JPEG 载荷 | 833,445 B | 833,445 B |
| base64 载荷 | 1,111,260 B（**+33%**） | — |
| JSON body | 1,111,373 B | 833,445 B |

放大效应（合成 1080p 夹具，最坏情况）：

| 观看者数 | 服务端串行开销 | 线上流量 |
|---:|---:|---:|
| 1 | 0.02 核 | 32 MB/s |

**风险**：低（服务端已存在 `get_latest_desktop_frame_raw`）。前端需处理认证头与 Blob 生命周期。

### 2.8 注册表与元数据持久化（P2，条件性）

**证据**（`crates/server/src/meta_store.rs:216-221`）

```rust
fn snapshot_locked(state: &StoreState) -> Snapshot {
    Snapshot { records: Arc::new(state.records.clone()), version: state.version }   // 全量克隆
}
```

实测扩展性（合成夹具）：

| 终端数 | `update_meta` ms | `list_terminals` ms |
|---:|---:|---:|
| 10 | 0.002 | 0.003 |
| 100 | 0.015 | 0.034 |
| 1000 | 0.144 | 0.401 |
| 5000 | 0.716 | 2.186 |

**重要澄清**（修正早期假设）：`update_heartbeat()`（`ws/registry.rs:176-193`）**只更新内存 session，完全不触碰 meta_store**。全量快照克隆只发生在：
- `record_registration()` —— **每次 Agent WS 连接/重连一次**（`ws/registry.rs:141`）；
- `update_meta()` —— 用户主动改名/打标签时（低频）。

因此**不存在"每次心跳 O(n²) 落盘"**。

**真实风险**：**重连风暴**。服务端重启后 5000 个 Agent 同时重连 → 5000 × 0.716 ms ≈ **3.6 s** 的连续全量克隆，且克隆在 `state.write()` 写锁内完成，会与其他元数据读写排队；同时 `try_send` 队列满后回退到 `spawn_blocking`（`meta_store.rs:203`），进一步放大压力。另外前端每 2 s 轮询 `list_terminals`（`index.html:2178`），5000 终端时 2.186 ms/次 × 观看者数。

**方案**
- 快照改为**写时复制**：把 `records` 外层换成 `im::HashMap` 或 `Arc<HashMap>` + 增量变更集，避免每次全量深拷贝。
- `list_terminals` 增加结果缓存（1–2 s TTL）或改用字段级快照，避免每次重算全表。
- 若长期规划支持数千终端，重新评估"单一 JSON 文件全量落盘"的持久化形态（分片或嵌入式 KV）。

**预期收益**：重连风暴下 CPU 峰值下降一个数量级；`list_terminals` 高频轮询成本趋近于零。

**风险**：低（当前规模下收益也小）。**建议按实际终端规模决定是否排期**——若目标场景是数十台，可只做缓存；若上千台，则必须处理。

## 3. 优化优先级与依赖关系

```
P0（建议立即，合计约 1.5 人日）
 ├─ §2.2 消除 1920px 悬崖 ──────────── 独立，零依赖，收益最大
 ├─ §2.1 抓屏前置判定 + 空闲退避 ────── 独立，Agent CPU -90%（静止场景）
 └─ §2.3 帧入库时预计算 base64 ──────── 独立

P1（依赖 P0 的度量基线）
 ├─ §2.6 提高去重采样密度 ─┐
 │                          ├── 需与 §2.1 退避策略联动调参
 ├─ §2.1 平台级变更通知 ────┘（可行性验证，工作量最大）
 ├─ §2.5 JPEG 编码器评估 ──── 必须在 §2.2 之后做，否则收益被像素数掩盖
 └─ §2.7 raw 二进制端点 ─┐
                          ├── §2.4 与 §2.7 应合并为一次传输层改造
     §2.4 WS 推送替代轮询 ─┘

P2（按终端规模决定）
 ├─ §2.8 注册表写时复制
 └─ §2.5（续）SIMD 编码器跨平台验证（含 Windows）
```

**三处硬依赖，不可打乱**：

1. **§2.2 必须先于 §2.5** —— 不先削减像素，就无法判断编码器优化的真实增益，测量会被像素数淹没。
2. **§2.4 与 §2.7 必须合并** —— 二者都指向"用二进制 WS 替代 HTTP+base64+JSON"，分开做等于把同一段传输层改两遍。
3. **§2.1 必须先于 §2.6** —— 提高去重灵敏度会让更多帧进入编码路径；若不先做空闲退避，CPU 反而上升。

## 5. 未覆盖与需进一步验证

1. **显示器缩放因子（HiDPI）**：本机为 `scale 1.0`。Retina 下 `capture_image()` 返回的是逻辑尺寸还是物理像素，会直接改变 §2.2 的阈值语义与像素总量，**必须复测**。
2. **Windows / Linux 抓屏路径**：本报告全部在 macOS 实测。Windows 走 DXGI Duplication，其抓屏成本与抖动特性可能完全不同，§2.1 的结论需在 Windows 上重验。
3. **多显示器与坐标换算**：未覆盖。
4. **输入反向通道延迟**：本次只测到"每个输入事件写一条审计"（0.0079 ms/条，可忽略），未测端到端 RTT（浏览器事件 → 注入生效 → 像素回流）。前端输入节流为 35 ms（≈28 事件/s），这一环的体感延迟值得单独测量。
5. **`scale` 协议字段**：从 server 到 agent 全链路被丢弃（已定义未实现），确认属于未完成特性而非性能问题。
6. **本报告所有绝对值均为单机测量**，用于比较不同方案的**相对增益**可靠；跨机器直接套用绝对值请谨慎。

## 7. 一句话总结

> at-pc 的推流链路**结构是对的**（独立抓屏线程、二进制 WS 帧、背压丢弃、后台写盘、审计异步化——这些都已落地），但存在三个"配置级"的浪费：**抓屏后才判断静止**（静止画面烧 32% 核）、**1920px 阈值让最主流分辨率不降采样**（3.5x 时间 / 2.9x 码流）、**每轮询重算 base64**（21.6x 于必要成本）。三者合计修复成本极低、风险极低，而收益覆盖了当前绝大部分可优化空间。
